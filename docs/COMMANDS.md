# Useful commands: Desk

Every command a person or an agent runs day to day, with what it does and when. Keep it current: a command that no longer exists is a defect. Type `drew` on Windows (`desk` is the same program elsewhere).

## Daily
| Command | What it does | When |
| --- | --- | --- |
| `drew-ui` | starts the web UI on http://127.0.0.1:8765 (`DESK_UI_PORT` to change, `DESK_HOME` for the store). `Ctrl+C` in its terminal stops it within about 2 seconds even with a browser tab open: open event streams end at shutdown and connections are cut after 1 second | every session |
| `drew stop [--port N]` | ends whatever listens on the UI port (default 8765 or `DESK_UI_PORT`) by PID and prints `PID n stopped`; exit 0 and "nothing listens" when nothing does; it does not look at the process name, so it stops any program on that port | before a refresh, or when `Ctrl+C` is not at hand |
| `drew refresh [--ref REF] [--repo PATH]` | one command for stop, install, start: stops the UI as `drew stop` does, runs `uv tool install --force` on the repo (or on `git+file:///<repo>@REF` for a branch, tag or commit; an unknown ref is refused before anything is stopped), starts `drew-ui` again and prints `drew --version`. On Windows, from uv's tools folder, drew.exe cannot replace itself, so a detached `desk-refresh.cmd` does the install after the command exits, opens drew-ui in its own window and writes `desk-refresh.log` (temp folder) ending with the version | after merging or checking out new Desk code |
| `uv run --no-sync pytest -q` | runs the whole test suite | before every report |
| `drew validate` | schema, lifecycle rules, dependencies, track values; a blank assignee on an open ticket is a warning `no assignee (James has not scanned this)` until `[rules] assignee_required_from` in `desk.toml` (default 2026-11-22), an error from that date; exit 1 on errors. It also warns on a ready, claimed or in-progress ticket with `ui` in its `dod` and no ticket assigned to chaz among its `depends_on` or `related` (user-facing work is designed by Chaz first; bug tickets, Chaz's own tickets and a Context line `design: none - <reason>` are exempt), on undispatched work (see `drew dispatch`), on a ready ticket whose `## Commands` is empty or still the placeholder, on a ticket with `ui` in its `dod` that is in review with no screenshot in Attachments, and on text that is hard to read (DESK-0253, standards rule 15, "Human-readable by default"): the Context, Outcome or How to validate of an open ticket above Flesch-Kincaid grade 10, or using bone, lane, slice, DoD, fixture, ADR, flush, fetched or "in your mouth" with no gloss beside it (a warning, never an error; code spans, quotes and ids are not read), and on text that breaks the formatting ladder (standards rule 15): a Context, Outcome or Report over 1,200 characters in one block (`readability`), or over 4,000 characters (save it as a Markdown file and link it). DESK-0209 (no plain blocks, James 2026-11-09): one warning per free-text section (Context, Outcome, Prompt, Out of scope, Report, Evidence) that holds a wall of text, `<ID>: <Section> has a wall of text (N characters); use a bold lead and bullets (rule 15)`: a prose paragraph over 300 characters, or three or more sentences over 200 without a bold lead, or a list item over 400; blockquotes, code, tables and headings never count, and the ticket page shows the same flag in plain words beside the section's heading. DESK-0215 (GPS, James 2026-11-09): one warning per ticket past triage (ready onward; inbox, triage, done and rejected are not scored) that fails Goal, Proof or Steps, `<ID>: GPS fails G, P and S: <why>`. G: the Outcome opens with one sentence (after an optional `**Goal.**` marker or bold lead) of at most 30 words; P: an Acceptance checkbox line and a How to validate line that names something observable (run, open, prints, shows, lists, returns, see); S: the Prompt has steps and none hides behind a handwaving word (handle, deal with, clean up, improve, optimize, figure out, as needed, as appropriate, etc., and so on, various, relevant, somehow, make sure it works, TBD). A project profile's `gps:` block changes the defaults for its tickets: `goal_max_words`, `proof_requires` (`observable`, `command` = a backticked span in How to validate, `screenshot` = the word or an image file in How to validate, Evidence or Attachments, any other word = it must appear in the Proof), `extra_handwaving`, `allow`. DESK-0208: `parent:` is an error when it names a ticket that does not exist, the ticket itself, or a chain that loops back; a warning when the main ticket is itself part of another (one level is enough) and when a main ticket is done or approved while one of its subtickets is open | before every commit |
| `drew validate --signoffs` | lists every sign-off (a comment starting `Sign-off (`) as `ID  when  author  state`, state one of `verified` (token matched and the signature checks against the key on this machine), `unverified` or `impersonation suspected`; only verified ones count; exit 1 unless all are verified | before relying on a sign-off |
| `drew token ACTOR (--out PATH \| --pubkey FILE) [--rotate]` | DESK-0259, DESK-0262: registers an actor's SSH public key (the actor is a people.yaml key). `--out` makes a new Ed25519 pair with `ssh-keygen` and writes the private key to PATH for the actor to keep; `--pubkey` registers the actor's own OpenSSH public key. Desk stores public keys only, `<actor>.pub` in `DESK_KEYS_DIR` or `~/.desk/actor-keys/`, so nothing in that folder can sign. The actor puts `DESK_ACTOR=<key>` and `DESK_ACTOR_KEY=<path to its private key>` in its own environment. A `drew comment` made with the matching private key is stamped `via=verified ok=1 sig=<ssh-keygen -Y sign of actor, ticket, time and words>` and checked with `ssh-keygen -Y verify`; any other is `via=claimed ok=0`. Signatures use OpenSSH (ships with Windows 10/11, macOS and Linux) rather than the `cryptography` package, which is not a Desk dependency. Only the store owner may run it, confirmed by the OS user in people.yaml at their own terminal: it is refused (exit 1, nothing written) when CLAUDECODE, CLAUDE_CODE_SESSION_ID, DESK_ACTOR, DESK_SUBAGENT_ID or DESK_ACTOR_KEY is set. Every issue or rotation is a `key-issue` or `key-rotate` line in `.desk/writes.jsonl` with the key fingerprint and who asked. Limit: a process running as the same OS user that strips its environment is not stopped; the log line is how such a rotation is seen. A comment written from a session id that already wrote under a different author is stamped `impersonation=suspected` | once per actor; `--rotate` when a private key leaks |
| `drew search "words and filters" [--limit N] [--json]` | finds tickets by part of an id or title (an FTS5 trigram index in `.desk/search.sqlite`, rebuilt incrementally from the files): `DESK-00`, `0038` and `chedul` match inside ids and words, a misspelling such as `shceduler` finds the closest spelled words in titles. Filters, mixed with words in any order: `project:` `status:` `type:` `tag:` `ask:` (approve, choose, answer, provide, review) `owner:` `assignee:` `track:` `sprint:` `priority:` `is:stale` `is:open` `is:closed` `before:DATE` `after:DATE` (both on the `updated` date); `a,b` means either, a leading `-` leaves one out, quotes hold a name with spaces (`track:"first real use"`). Results are grouped by project with counts, open before closed, then p0 to p3, exact id first. `parent:DESK-0183` lists that main ticket's subtickets, and a subticket's hit says `part of <ID>: <title>` (DESK-0208) | finding a ticket without remembering where it is |
| `drew outbox --for <actor> [--since last-entry\|DATE\|"DATE HH:MM"] [--json] [--posted]` / `drew outbox --all` | the entry for one coworker thread's team folder (rule 25 header: Date, From: Patch, To, Expires a week out, Supersedes, `Tickets:` listing every id), then one line per ticket: `id · title · status · change · ask: <kind> by <date>`. A ticket is listed when it was assigned or reassigned to the actor since the cut-off, when Patch or James commented on or decided a ticket the actor touched (assigned to them, owned by them, or commented on by them), when it changed after the actor last acted on it, or when it is new and names the actor in Context or Prompt. The ask is `do`, `review` or a decision's approve, choose, answer, provide, with the review-by date, when the ticket is assigned to the actor and open. The cut-off per actor is kept in `.desk/state` (`outbox`); printing does not move it, `--posted` moves it to now (use it when the entry is posted) so the next entry starts where this one ended; with no earlier entry it looks a week back. `--all` prints one entry for every coworker in `people.yaml` that has changes; `--json` is for the poster (actor, cut-off, tickets with changes, text) | after a sweep, to tell each thread what to look at |
| `drew sprint new NAME [--start DATE] [--end DATE] [--owner WHO] [--project KEY] [--note TEXT]` / `drew sprint list` / `drew sprint show NAME` | sprints in `sprints.yaml`: parallel, named like `sprint 6 2026`, across projects and tracks. A sprint is identified by its name and its project (no `--project` means it spans projects), so the same name can exist in two projects. `list` shows each sprint with its tickets and open count; `show` prints its tickets in score order (p0 first, then the sooner review-by) and the burn-down numbers (done, remaining, days left, ideal remaining today, a remaining/ideal figure per day). A ticket joins with `drew move <ID> --sprint NAME` (it must exist; `--sprint ''` takes it out; `--to` may be given too), which sets the `sprint:` field. `drew validate` warns when a ticket names a sprint that is not in `sprints.yaml`; `drew list --sprint NAME` filters; the Previous and Next walk "Within this sprint" uses the field | planning a sprint |
| `drew history <ID> [--by DIM] [--filter KEY=VALUE ...] [--json]` | DESK-0171: the ticket's timeline from its activity log (`events/<ID>.jsonl`, DESK-0162): `Latest change: <who> (<kind>) · <what> · <when>`, then every event newest first, one line each: when, who and their kind (Owner, Main session, Coworker, Code session, Subagent, Person), where from (on the page, command line, from old comments, from git history), what (a field old -> new, a section, a comment's first line, created). `--by` actor, kind, source, project, company, track, sprint or field groups the events under that value with counts (a coloured dot per group in a terminal); `--filter` keeps only matching events (repeat it for AND; `a,b` means either; the key or the label works: `kind=coworker`, `actor=james`); project, company, track and sprint are the ticket's values when the event happened. An empty log says to run `drew migrate events --apply` | what happened to a ticket, and who did it |
| `drew whoami [--as WHO] [--json]` | how this command line would be recorded on a write: actor, kind (person, thread, session, subagent), instance, source (cli) and how it was established. Order: `DESK_SUBAGENT_ID` (a subagent is `subagent:<id>` with its parent from `DESK_PARENT_SESSION`, never Patch or James), then a name given (`--as`, or `DESK_ACTOR` with optional `DESK_ACTOR_KIND`), then a Claude Code shell (`CLAUDECODE`, the session id from `DESK_INSTANCE` or `CLAUDE_CODE_SESSION_ID`), then the operating-system user and then git `user.name`, each matched to a person in `people.yaml` (`os_users:`). Only the last two are **confirmed**; a name that is only typed is **claimed** and says so. Every write appends a line to `.desk/writes.jsonl` (ticket, actor, kind, instance, source, how, confirmed, as, parent), and every comment carries a hidden `<!-- by ... -->` tag that `drew comments` prints as `[person · cli · os-user · confirmed]` (`not recorded` for older lines; `--json` has an `identity` object) and the ticket page shows beside the author | telling two sessions apart |
| `drew refine <ID> "line" [--review-by DATE --reason TEXT] [--as WHO]` | a tracked refinement of the requirements: adds `- [ ] <date> refinement: <line>` to Acceptance and a dated note to Comments. A refinement may cost time, so `--review-by` moves the date, but only with `--reason`, and the slip (old date, new date, why) is written to Comments. Scope never changes this way: that is `split`. Not for closed tickets | when a requirement gets clearer |
| `drew split <ID> --title "..." [--size xs\|s\|m] [--due DATE] [--details "..."] [--outcome "..."] [--acceptance "..."]... [--as WHO]` | a change of scope does not edit the ticket; it becomes a new ticket (same project, type, priority, dod, tags, assignee; `split_from: <ID>`; review-by = `--due`) that `depends_on` the old one, while the old one lists it under `blocks`, gets a note in Comments, and a prompt in Decision asking for the completion decision: done as scoped, or closed in favour of the new ticket (`drew reject`). The ticket page has the same two actions under Acceptance (Refine or split); a ticket that is thrown (ready or later) refuses a rewritten Outcome with a pointer to Split. The weekly review ticket's Report lists the splits made that week | when the scope changes |
| `drew repeats [--apply]` | the repeated-ask detector (rule: repetition is an emergency). A repeated ask: the store owner commented twice on one ticket within 7 days asking for the same outcome (normalized text: lower case, no punctuation or filler words, at least three content words each, 60% shared); writing the second comment already makes the ticket p0 with the tag `emergency`, `drew validate` warns `repeated ask` while the pair stands, and `--apply` escalates any that were written before this existed. A stale hand-off: `blocked_on` names the owner and the ticket file has not changed since before the second-to-last sweep (sweep times are kept in `.desk/state` by `drew comments --mark-sweep`): `waiting on James since <time>; is the hand-off real?`. `drew comments --mark-sweep` prints these as `FLAG ...` lines before anything else | the sweep |
| `drew dispatch [--json]` | the tickets nobody has started: status `ready`, assigned to Patch, every dependency in review, approved or done, `blocked_on` empty, and the file unchanged for more than an hour; grouped by repository (the project profile's `repo:` line, else the project key), the repo with the longest wait first, oldest ticket first, each with id, size, effort, waiting hours and dependencies. `drew validate` warns on the same tickets (`undispatched for N h`); setting `blocked_on` to the worker's name or a reason silences it. The wait is read from the ticket file's modification time, since `updated` holds only a date | at the start of a sweep, and whenever a delivery makes tickets ready |
| `drew assign-rules` / `drew assign-rules init [--force]` | shows the auto-assignment rules (`assign.yaml` in the store, else the built-in table: decisions and human review to james, design review and brand to chaz, security to bigd, research to em, tech and product to lily, calendar, orders and admin to bri, legal, finance and channel to joe, a project session keeps `code:<project>`, build work falls back to main); `init` writes `assign.yaml` to edit. `drew new` and `drew intake` fill a blank assignee when the rules name exactly one person (two different people leave it blank and print a warning); a rule never changes an assignee someone set; the ticket page says "assigned by rule <name>" until a person changes it | setting up, or changing a mapping |
| `drew people` / `drew people init [--force]` | lists the people an owner or assignee can be, in the groups of the dropdown (People, Code sessions, People outside the team), with kind, colour and role. They come from `people.yaml` in the store, or the built-in team (james, main shown as Patch, chaz, em, bri, joe, lily, bigd, and the `code:<project>` sessions) when there is none; `init` writes that team to `people.yaml` to edit. If `~/.claude/jeby-private/people.yaml` exists (or the file named by `DESK_PRIVATE_PEOPLE`) its people are added, kind `external` unless it says otherwise; it is read, never copied into the store, and a ticket holds only the key | setting up, or adding a person |
| `drew list [--project] [--status] [--assignee NAME] [--all]` | table of open tickets, with an assignee column; a subticket's title ends with `(part of <ID>: <title>)` (DESK-0208), so `drew list --assignee chaz` shows Chaz's pieces of bigger tickets | start of a session |
| `drew list --sort score` | the same table ordered by the priority score, highest first (DESK-0135; docs/PRIORITY.md). Every `drew list` carries a `score` column (blank on a closed ticket); hand-set priority is one input to the score, not the order | to see what Desk would do next, across projects |
| `drew explain <ID>` | why a ticket scores what it does (DESK-0137): the score and its band, the top three reasons in plain words, then every term with its points and which level set its weight (default, store `[priority]`, track rules `weights:`, project `priority:` block, private file). The private people file is reported as present or absent, never printed | when a ticket sits higher or lower than expected |
| `drew list --due DAYS` | the open tickets with a hard deadline within DAYS days or already missed, soonest first, each with the date and days left in words (`due in 3 days`, `missed by 2 days`): the same set as the Immediate Action Required row on Today (`drew list --due 14`). Soft and sprint deadlines, closed and approved tickets are left out | to see what cannot slip, from the terminal |
| `drew deadline <ID> <YYYY-MM-DD> --hard \| --soft \| --sprint [--as WHO]` / `drew deadline <ID> --clear` | sets `deadline:` and `deadline_kind:` on the ticket and writes a dated line to Comments. `review_by` stays the soft date to look again; only a hard deadline reaches Today's Immediate Action Required row (top of Today: hard deadlines in the next 14 days or missed, soonest first, five then "N more", red when one is missed). `drew validate` checks that the date is a date, the kind is one of hard, soft, sprint, and that one never appears without the other. `drew new ... --deadline DATE [--deadline-kind hard\|soft\|sprint]` sets it at creation (kind defaults to hard) | when a real date appears |
| `drew assign <ID> --to NAME [--note "..."] [--handoff URL_OR_DOC_ID] [--as WHO]` | sets `assignee` (a display name such as `Patch` or `Big D` is stored as its key, `main` or `bigd`; see `drew people`), `assigned_at` and `assigned_by`, optional `handoff`, appends `- <date> · <actor> · assigned to <name>: <note>` to Comments. Done means: assignee named and notified; the hand-off record linked | handing a ticket to someone |
| `drew comment ID "text" [--kind Question\|Suggestion\|Concern\|FYI] [--as name]` | adds a dated, timed comment that always has a kind (Question unless you say otherwise), kept at the end of the line as `<!-- kind: Concern -->`; the same words from the same author within 10 minutes, whatever the kind, are refused as a duplicate | any time; the same person posting the same words again is ignored: within 10 minutes when identical, within 60 seconds when only case, spacing, punctuation, brackets, a trailing number or a typo or two differ (`Dup test # 2 ()` is `Dup test # 2`), and `james`, `james1` and `james_` count as one person; the earlier comment is named and the UI highlights it |
| `drew comments [--author NAME] [--since DATE\|"DATE HH:MM"\|last-sweep] [--unanswered] [--answered-by NAME] [--json] [--mark-sweep]` | lists comments across the store (ticket, time, author, kind, text; `--json` gives a list with ticket, title, when, author, kind, text, answered). `--unanswered` keeps comments with no later line by patch in the same ticket and no change to the ticket on a day after its last comment (dates are days, so a same-day change leaves it open). `--since last-sweep` reads `.desk/state` (everything when none is marked); `--mark-sweep` records now as the last sweep after listing, or alone just records it. The Today page shows the owner's open count in an "asked" block and the weekly review ticket's Report carries it | the sweep, first: `drew comments --author james --since last-sweep --unanswered`, answer each, then `drew comments --mark-sweep` |
| `drew needs-me [--as NAME] [--json] [--seen ID...] [--seen-all]` | the tickets with an ask for you (a decision ticket you hold, a review only you may approve, a ticket you hold to do) and the tickets someone else changed since you last acted on them (a comment, a checked line, a status, Report or proof change); each with its reason line (`ask: approve · from Patch · due Mon`, `changed: 2 comments by Lily · 5:10 AM`) and a closing `N asks for you · K changed by someone else`. Reading a ticket never counts as acting. `--seen ID` is Mark seen (clears a change without acting; asks stay until answered), `--seen-all` clears every change | start of a session, before the comment sweep |

| `drew migrate commands --dry-run` / `--apply` | gives every ticket without a `## Commands` section one, right after How to validate, seeded with the How to validate lines that look like commands (a line, or a backticked span, that starts with `drew`, `uv`, `pytest`, `git`, `python`, `npm`, `curl` and the like), one bullet in backticks each, or the placeholder "- none yet (a worker adds the exact commands it ran)" when there are none; a ticket that already has the heading is left alone; the dry run prints each ticket with what it would write and the counts | `--apply` adds only the `## Commands` section; `updated` untouched and the file's line endings kept; running it twice writes nothing the second time |
| `drew migrate tests --dry-run` / `--apply` | gives every ticket without Tests text a `## Tests` section (right after How to validate) holding "The How to validate lines, performed by a person, are the test until an automated one exists."; the dry run lists the tickets and the count | `--apply` changes only that section (`updated` and line endings untouched); a ticket with its own Tests text is left alone; running it twice writes nothing the second time. `drew validate` warns on a ready, in_progress or review ticket with no Tests text, the ticket page shows the section under How to validate, and the weekly review ticket's Report counts open tickets still on the seed |
| `drew migrate assignee --dry-run` / `--apply` [`--include-closed`] | fills blank assignees from `assign.yaml` (built-in table when there is none); the dry run lists ticket, assignee and rule, then counts per rule, the tickets left blank because two rules disagree and those no rule matches. `--apply` writes only `assignee:` and `assigned_by: rule:<name>` into tickets whose assignee is blank, never changes one that is set, leaves `updated` alone, and writes nothing the second time. **Blank is James's not-yet-scanned marker: run `--apply` only when he says** | after the assignee dropdown ships |
| `drew migrate events --dry-run` / `--apply` | DESK-0162, DESK-0045: turns every ticket's dated Comments lines (date, time when written, author, first line, the identity tag when there is one) and every git commit that touched its file (one `git log` call over `tickets/`; author mapped to a person in `people.yaml` where the name, alias or OS user matches) into events in its activity log, `events/<ID>.jsonl`; progress on stderr every 200 tickets, then the table per ticket (comments, git commits, events) and one plain sentence. A store that is not a git repository gets the comments and a note | `--apply` writes each event once, keyed by the comment line or the commit, so a second run writes nothing; the dry run counts exactly what `--apply` would write. Every save made since DESK-0162 appends its own events (field old -> new, section, comment first line, created), never inside the ticket markdown, never edited: each line carries its number and a hash of the line before it |
| `drew migrate type --dry-run` / `--apply` | retires the legacy `slice` and `chore` types by rule; the dry run prints ticket, old -> new and counts | `--apply` rewrites only the `type:` line |
| `drew new --project key --type feature "title"` | types: feature, upgrade, bug, task, docs, decision, research, intake, release; writes the `How to validate`, `Commands` and `Tests` headings (a hint, the placeholder, a hint) | write the steps before the work starts |
| `drew sub <PARENT> "title" --assignee <who> [--project KEY] [--type task] [--priority p0..p3] [--size s] [--owner main] [--dod core]` | DESK-0208: a subticket, a piece of a main ticket (an icon from Chaz, an input from James), written through the same writer as `drew new` with `parent: <PARENT>`. It lands in the main ticket's project at its priority, as a `task`, unless the flags say otherwise (any project is allowed); with no `--assignee`, `assign.yaml` may fill it. It prints the file path and `<ID> is part of <PARENT>: <title>`. Refused in plain words when the main ticket does not exist, is itself a subticket (one level is enough) or is done or let go. A subticket is tracked like any ticket but stays off `/board`, `/projects`, the company rows and Today's counts; the main ticket shows `Subtasks: N of M done` | a piece of a bigger ticket that someone else does |
| `drew rename-project old new` | renames a project; ids stay, old key and prefix become aliases | |
| `drew intake <folder-or-zip> --topic x --project key` | copies a hand-off into `intake/` and opens a ticket | refuses private files |
| `drew intake --check <SLICES.md>` | checks the ticket-ready table (shape of standards/templates/UPDATE.md): required columns, known project keys, type, size, ask (`choose · YYYY-MM-DD`, required on decisions), Depends on ids (a row in the file or a ticket in the store), non-empty Acceptance and How to validate; prints each problem with its row id, writes `<file>.check.md` beside the input, exits 1 on errors | imports nothing; Drive's `\|` escapes are undone first. An entry with the rule 25 header (`Date: ... · From: ...`) that has a ticket table or a Deliverables line must carry real ticket ids on its `Tickets:` line: empty, missing, `none`, `TBD` (even inside a sentence such as `id TBD`) or no id at all is an error that names rule 25 and the fix (ask Patch for the id first); a question-only entry may say `Tickets: none` and needs no table |
| `drew sync` | with `[git] sync = true`: pulls, commits what is pending now (without waiting for the idle time) and pushes | `[git] debounce_seconds` (default 30) is the idle time after which pending changes are committed on their own: by a timer in the UI, at the next start of any command otherwise. A stop in between loses nothing |
| `drew index` | rebuilds `.desk/index.sqlite` | derived, gitignored |
| `drew bench --search-rows N` | times search over N synthetic rows held in memory (50000 is the budget case) and prints p50 and p95 against the 50 ms budget | before and after any change to `src/desk/search.py` |
| `drew bench --tickets N [--runs R] [--out file.json] [--save-baseline]` | builds a throwaway store (30 projects with brand blocks, N tickets of about 3.4 KB) in a temp folder, drives Today, board and a ticket page through the app, times `next_id`, `new`, `move` and reindex, prints p50 and p95 per path against `src/desk/bench/budgets.toml`, deletes the folder | before and after any speed change; `uv run --no-sync pytest -m bench` runs the 1,000-ticket case and fails on a broken budget or a p50 more than 20% over `src/desk/bench/baseline.json` |

## Build, release, docs
| Command | What it does | Notes |
| --- | --- | --- |
| `uv build --wheel` | builds the wheel; the build hook writes the commit into `desk/_build.py` | the footer and `drew --version` read it |
| `drew --version` | prints `Desk <version> · <commit or "no git">` | same text as the UI footer |
| `drew doctor [--repo PATH]` | installed version and commit, repo path and HEAD, the active YAML loader (libyaml or pure Python), tool path, store path, anything listening on the UI port; exit 1 when the installed code is older than the repo | run it when the UI looks out of date |
| `drew upgrade [--repo PATH]` | refuses while a process listens on the UI port (names the PID), then runs `uv tool install --force <repo>` and prints the new version. On Windows, when drew runs from uv's tools folder, it instead writes `desk-upgrade.cmd` to the temp folder and starts it detached (it waits 2 s, installs, logs to `desk-upgrade.log`, and on failure logs the restore command) and exits at once | stop the UI first; on Windows wait about 30 s, then `drew doctor` |
| `drew review new` / `drew review sync` | creates, then refreshes, this week's ticket review | weekly |

## Troubleshooting one-liners
| Symptom | Command |
| --- | --- |
| port in use | `drew doctor` shows the PID; then `taskkill /PID <pid> /T /F` (Windows) or `kill <pid>` (never a broad name match) |
| stale install | `drew doctor`, then stop the UI and `drew upgrade` |
| `No module named 'desk'` after an upgrade | `uv tool install --force --reinstall <repo>` (also printed by `drew doctor`) |
| "no git" in the footer | the wheel was built outside a git checkout; rebuild from the repo |
